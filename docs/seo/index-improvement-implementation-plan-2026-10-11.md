## 3. 外部canonicalの調査手順

対象：`/ranking/rent-cheap/yamanashi`。現行自己canonicalと、6/21時点のGoogle選定 `https://www.747live.bet/` を区別する。

1. GSCのURL検査で「公開URLをテスト」。取得HTML・レスポンス・スクリーンショットに、日時とURLを添えて保存。ライブ検査だけではGoogleのcanonical選定を予測できない。
2. Gitの初期コードに自己canonicalがあることを証跡とし、6/21の本番deploymentのcommit・aliases・応答記録が残っているかVercelで照合。保持期限で取得不能なら「未確認」と記録する。履歴がないことを正常の証明にしない。
3. 通常UA/Googlebot UAの200応答、canonical、robots、外部redirect、HTTP Linkヘッダーを再確認。UA差がないことだけで全配信経路の正常を断定しない。
4. 配信異常が見つかった場合のみ原因箇所を修正。現在正しいcanonicalを別形式へ変更するだけのPRは作らない。ライブ検査が正常なら登録リクエストを1回実施し、7/14/28日後の最終クロールとGoogle選定canonicalを記録する（本計画では未実施）。

セキュリティ問題・手動対策は前回確認で問題なし。侵害・外部コピー・Google判定のどれかを原因と確定する証拠はまだない。未解決でも、独立したPR-A〜Cの準備は進められる。

## 4. PR-A：継続計測とリンク監査

### 設計

- 新規 `scripts/gsc/inspectUrls.ts`：既存 `auth.ts` のreadonly認証を再利用。サイトURL・入力CSV・出力先を引数化。スクリプト専用でクライアントへ認証情報を渡さない。
- 元の370 URLを固定コホートとして保持し、検査時刻、coverageState、verdict、robots、fetch、user/google canonical、lastCrawlTimeを保存。エラーを「未登録」に置換せず、取得失敗として別列へ。
- 初回の日次枠は既に1,719件使用したため、今日の追加検査は残枠を確認してから。通常は週1回370件、429/5xxの再試行と再開用キャッシュを用意。サイト全3,139件の毎日検査はしない。
- `scripts/gsc/inspectDiff.ts`：同じURLの状態遷移と再クロールを出力。登録済み4件を含む元コホートと、その時点の未登録群を分ける。文字列の日英依存を避け、取得可能な構造化フィールドを優先する。
- `scripts/gsc/auditLinks.ts`：本番またはビルド出力の同一origin HTMLから通常の `a[href]` を抽出。フラグメント除外、相対URL解決、クエリ有無を別集計。トップ→ランキング一覧→全国版→県版等の最短深度、参照元数、参照元HTTP状態を記録。地図選択用クエリを無差別にクロールしない。
- まず検出のみ93件（うち県ランキング72件）と参照元を監査。到達不可・壊れたリンク・canonical不一致が見つかれば個別修正。正常ならリンク増設を見送り、再クロールを観測する。

### 検証と評価

認証をmockしたテストで、状態遷移、欠損フィールド、エラー分離、CSV入出力、再開、429を確認。リンク監査は相対/絶対/クエリ/フラグメント/外部URLのfixtureで検証する。

主要指標：固定群の登録数、検出→クロール済み件数、最終クロールが公開後へ更新された件数、異常canonical件数。GSCページ別表示・クリックは別指標として結合し、表示ゼロを未登録扱いしない。GA4の新イベントはこの監視には不要。

## 5. PR-B：実際のページ更新日時をsitemapへ

### 現状の問題とモデル

`asOf` は統計対象の時点であり、サイトがそのデータを取得・公開した時点ではない。`new Date()` のfallbackも未変更ページの日時を動かす。更新日時を証明できないページは `lastModified` を省略してよい。URLの掲載は維持する。

新規 `lib/pageRevisions.ts` または `data/page-revisions.json` に、URL/テンプレート範囲/データ配信範囲ごとの更新履歴を管理する。履歴の単位は `{scope, publishedAt, evidence}` とし、証跡はproduction deployment ID・commit・変更理由。自治体データスキーマへのフィールド追加はしない。

- URL固有：新設または個別主要変更の本番反映時刻。
- テンプレート範囲：主要本文や構造化データ等の変更が実際に影響するページ群。同日同時更新は正確なら許容。
- データ範囲：更新ActionのJSON差分をもとに、影響する自治体/県/ランキング/地図へ本番公開時刻を紐付ける。元統計の年度を更新日時へ変換しない。
- ページごとに該当する確認済み時刻の最大値を採用。未来時刻、無効日付、証跡のない推定日は不採用。
- 過去履歴を復元できないページは日時を省略。今回の本番公開で全URLを更新扱いにしない。まず地図9 URLの確定履歴と、今回実際に変える `/map` を登録する。

`lib/dataFreshness.ts` の `parseAsOf` / `latestAsOf` は本文の基準年表示に既存利用があるため維持。sitemapでの `muniLastModified` / `latestLastModified` 利用を置換し、用途を明確にする。`withTemplateRevision` 等は全参照を確認して整理する。

### 運用と確認

実装PRには対象範囲と更新理由を含め、production deploymentの確定日時を公開手順で履歴へ反映する。未知のデプロイ日時をPR作成日で代用しない。データ更新Actionの自動追記は別段階とし、それまでは公開担当が差分に応じて履歴を記録する。管理不能な範囲には日時を出力しない。

変更：`app/sitemap.ts`、更新履歴manifest、`tests/app/sitemap.test.ts`、`tests/lib/dataFreshness.test.ts`、新規履歴テスト、運用ドキュメント。Actionへ接続する段階では `docs/data-update.md` を先に確認する。

テストは現在の「日付は分散する」「テンプレ日と同じにならない」から、証跡のある更新のみ反映・未変更URL不変・同時実更新を許容・未来日拒否・不明日省略へ変更。URL数・重複なし・canonical URLとの一致を保持。ビルド後XMLと本番XMLを比較し、日付変更/省略の対象をレビューする。

効果仮説：正確な更新信号で再取得の判断を助ける。7/14/28日後の地図3件のクロール日と登録を追う。日付修正だけで登録や順位が改善すると保証しない。

## 6. PR-C：汎用地図の説明設計

対象 `/map`。`HomeShell` に渡すサーバー描画childrenの先頭へ、既存 `HomeLinks` と重複しない説明を追加する。全自治体データをクライアントへ送らない。

具体的な文言案：

- H1「全国の自治体を地図で比較」
- リード「家賃・地価・人口などの公的データを、地図の色分けで比べられます。地域を検索するか、地図上の自治体を選ぶと詳しい数値を確認できます。」
- H2「比較できるデータ」：既存 `MAP_HUBS` の名称・URLを利用し指標別説明へリンク。災害リスクは重ね合わせ表示であることを明記。
- H2「数値の意味を確かめる」：「統計の基準時点や出典は指標・自治体によって異なります。家賃は募集物件の現在価格ではありません。データなし・対象外・区別非公表はゼロを意味しません。」→ `/about`。
- H2「使い方」：①地域を検索、②指標を切り替えて地図を確認、③自治体の詳細・出典を確認、④候補を追加して比較。操作ラベルは実装時に本番と一致させる。

PCでは現在の地図下の説明領域、モバイルでは既存メニュー内に置く。地図を覆う広告風の導入画面は追加しない。説明がメニュー内にあることをラベルで伝える。H1は1つ、説明は実際にユーザーが読める領域に配置する。

モバイルdrawerのキーボードフォーカス・閉じる操作・復帰先も確認する。閉じた画面外領域へのTab移動が起きるなら `HomeShell.tsx` のフォーカス管理を別の明示的な修正として扱い、クロール目的で操作不能な文字を隠して置かない。

ファイル：`app/map/page.tsx`、必要なら新規 `components/GeneralMapIntro.tsx`、`app/globals.css`。`components/MetricMapHub.tsx` と `MAP_HUBS` の既存構成を参考にする。家賃配色・欠損ヘルパー・データスキーマは維持。

## 7. 条件付き試験と公開順序

1. PR-Aで公開前基準値を保存。canonicalの個別調査を実施。
2. PR-Bを独立公開してXMLと更新日を確認。運用履歴が用意できなければ不明日時を省略する設計で進める。
3. PR-Cを別deploymentで公開し `/map` の実改訂日を記録する。日付修正と本文変更の効果は小標本・時間差でも完全には分離できないと明記。
4. 7/14/28日後に同じコホートを検査。GSC実績は確定済みの同じ28日窓で比較し、公開直後の部分日を除く。
5. 追加の本文試験は、対応できるクエリが複数観測され、既存 `buildHighlights` / `buildInsights` / 数値・出典に回答の不足が見つかった場合に選定。条件を満たすURLが10件なければ10件へ水増ししない。規模・県・需要・直前状態の近い未変更URLを対照にし、因果確定ではなく観察試験として評価する。

各PRはtypecheck・lint・関連テスト、公開前はCI全体とSSG buildを通す。既存の未コミットランキング変更・タイトル試験・比較導線と混ぜず、独立ブランチ/差分でレビューする。アプリ変更のロールバックでも、実更新履歴は過去の証跡として残し、巻き戻し公開も実質変更なら記録する。

## 出典（すべて2026-10-11確認）

- [Google：sitemap作成](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)：実質更新を表す正確なlastmodを使用、priority/changefreqは無視。日付の分散を要件とはしていない。
- [Google：canonical指定](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)：canonicalとサイトマップ等の信号を整合させる。サイト指定とGoogle選定は別。
- [Google：URL検査](https://support.google.com/webmasters/answer/9012289?hl=en)：登録済み情報とライブテストの差、ライブ検査の限界。
- [Google：リンクの推奨事項](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)：通常のa/hrefと内容に即した文脈を使用。リンク数の万能な目安はない。
- [Google：API上限](https://developers.google.com/webmaster-tools/limits)：URL検査はサイトあたり2,000件/日、600件/分。
- [IndexNow FAQ](https://www.indexnow.org/faq)：参加検索エンジンへの通知であり、Googleの登録を代替・保証する仕組みとして扱わない。
