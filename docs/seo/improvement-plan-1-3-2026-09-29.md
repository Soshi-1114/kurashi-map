## 3. 対応① 計測整備

### 現状と設計

- `shindan_run`は条件変更ごとに発生する。350件/22ユーザーを350回の診断完了と扱わない。
- 診断結果生成・スクロール・比較クリックのイベントはローカルに実装済み。重複実装せず、本番状態との差分を修正する。
- `tool_entry`は`from`付き着地のみを測る。通常の直訪問・検索流入を含む全ツール利用数ではない。
- 比較ページは`useSearchParams`から自治体コードを同期的に正規化している。「復元前にcount=0」という不具合は確認されていない。直アクセスと内部遷移の両方で実測する。
- 現在の比較対象変更はURLの`from`を落とす。成立イベントの送客元を失わないよう、入口で取得した送客情報をページ内で保持する。古い訪問の送客元を新しい直接訪問へ引き継がない。

### イベントの役割

| 段階 | イベント | 発火・集計の契約 |
|---|---|---|
| ツール着地 | 既存`tool_entry` | from付きの初回着地。比較では検証済みコードと件数を記録 |
| 診断操作 | 既存`shindan_run` | 条件変更。成果件数にはしない |
| 診断結果生成 | 既存`shindan_result_impression` | 結果が生成された事実。視認とは区別 |
| 診断結果視認 | 既存`shindan_result_scroll` | 最初の結果カード等の小さな対象の視認を検出。同一条件では重複発火を抑える |
| 診断から遷移 | 既存`shindan_result_click` / `shindan_compare_click` | 詳細/比較へのクリック。着地確認と区別 |
| 比較成立 | 新規案`compare_ready` | 有効な2自治体以上の詳細データ取得が完了し、比較表が描画された時。loading/error中は送らない |
| 比較表視認 | 新規案`compare_view` | 成立した比較表の先頭が実際に視認された時。③の主成果 |

比較イベントは正規化したコード集合単位で同一マウント中の重複を防ぐ。成果率はセッション内で重複排除するので、条件変更や再訪問でイベントが複数回発生しても成果セッションは1件。コード集合の順序変更だけでは別成果にしない。

診断の現在の視認監視は結果section全体の25%交差である。長い結果一覧では画面内に25%が収まらない可能性があるため、320〜390px幅の画面で再現し、小さな監視対象へ変更する。既存イベントの意味が変わる場合は、計測版と変更日を記録し前後を接続しない。

計測パラメータは`lib/analytics.ts`に集約する。比較には自治体件数・既存の`tool_source`・実験ID/variant・正規化した送客元パスを必要な範囲で付与する。送客元にはサイト内のpathnameのみを使い、自由入力や任意のURLクエリを送らない。GA4標準の`source`/`medium`は流用しない。

### 集計方法

| 指標 | 分母 | 分子 |
|---|---|---|
| 診断結果到達率 | 条件操作をしたセッション | その後に結果を視認した同一セッション |
| 診断結果遷移率 | 結果を視認したセッション | その後に詳細/比較をクリックした同一セッション |
| 比較表示成功率 | 2件以上を指定して比較へ着地したセッション | その後に`compare_ready`が発生した同一セッション |
| 比較導線の最終成果率 | ③の対象ランキングを閲覧したセッション | そのページの導線を経由し`compare_view`に到達した同一セッション |

GA4の探索で同一セッション・順序・対象URLを満たす集計が作れることを確認する。単なるイベント件数同士、総ユーザー数とアクティブユーザー数、GSCクリックとGA4イベント数を割らない。

必要なセッション集計ができない場合は、既存のエクスポート環境の有無を調べる。ユーザー単位のファネルしか得られない場合は「ユーザー単位」と明記して基準を変更し、セッション率を取得できたと報告しない。集計方法を確定できるまで③の効果判定を開始しない。新しい分析基盤の導入は初回20時間に含めない。

内部テストは既存のdebug運用等で識別し、評価レポートから除外する。フィルタの影響を確認する前に恒久的なデータ除外を有効化しない。過去のテスト混入分を後から正確に補正できたとは扱わない。

- [ ] API失敗・重複コード・無効コードで誤った成果が出ない。

## 4. 対応② 人口ランキング3ページのtitle試験

### 対象と変更案

基準値はGSC 2026-09-06〜10-03、ページ次元。現行のmeta titleは既に人口ランキング語を含み、県別は人口1位をdescriptionで回答している。追加テストは対象3URLに限って「掲載件数と1位」をtitleで明示する。候補文言の年・件数・1位名はビルド時の実データから作る。

| 対象パス | クリック/表示 | title案（ブランド名は末尾） |
|---|---:|---|
| `/ranking/population-most` | 68 / 10,267、CTR 0.66%、平均8.58位 | 市区町村の人口ランキング｜上位100・1位は横浜市【2025年国勢調査】 |
| `/ranking/population-most/hokkaido` | 78 / 6,606、CTR 1.18%、平均8.28位 | 北海道の人口ランキング｜全179自治体・1位は札幌市【2025年国勢調査】 |
| `/ranking/population-most/hyogo` | 35 / 4,274、CTR 0.82%、平均7.63位 | 兵庫県の人口ランキング｜全41自治体・1位は神戸市【2025年国勢調査】 |

実際の1位名・自治体数・freshnessを既存データから使う。全国版の「上位100」は既存の初期掲載数を表す。基準年や掲載数の整合が取れない場合は変更せず原因を確認する。現行GSCには対象3URLで十分な表示回数があるが、この値を本番反映前ベースラインとして固定し、対照候補は直近28日の順位帯・デバイス・クエリ構成を確認してから決める。

対象は明示的なallowlistで限定する。`lib/rankings.ts`の共通title定義だけを変更し、全国・47県へ意図せず展開する実装は避ける。本文・description・canonical・H1は試験中固定する。現在のmetadataはtitleをOG/Twitterにも共有しているため、今回の検索title試験では旧ソーシャルtitleを維持するよう生成を分ける。

### 試験設計

- 実験ID: `population-title-2026-10`。
- 前期間: 本番反映前の連続28日。後期間: 反映翌日から28日。再クロールや検索結果のtitle反映遅れを記録する。
- 対照候補: 同じpopulation-mostの大阪・千葉・福岡（直近28日: 大阪2,473表示/CTR2.35%/7.28位、千葉2,988/1.34%/8.58位、福岡2,245/1.56%/7.57位）。対象3URL（全国0.66%/8.58位、北海道1.18%/8.28位、兵庫0.82%/7.63位）とのクエリ・device構成を追加取得して、順位帯が近い県ページを対照として固定する。全国版には同等の対照がないため、参考比較として扱い、因果効果を断定しない。
- 主指標: 試験群合算のCTR。個別URLのクリック・表示・平均順位、デバイス別と共通クエリ別も併記する。CTRの単純平均は使わない。
- 既存GSCスクリプトはpage-queryとdeviceを別々に取得する。URL×query×deviceの評価には、対象URLでフィルタした追加取得を用意する。取得できない内訳を推定して埋めない。
- 実際の検索表示titleは書き換えられる可能性がある。代表クエリを記録し、変更未反映を「訴求が無効」と判定しない。

**採用目安:** 合算CTR +0.3pt以上で、共通クエリ・デバイスでも改善方向が一致し、対照や順位変化だけで説明されないこと。基準は実務上の目安であり有意差の保証ではない。クリック・表示の実数と不確実性を併記する。母数不足・順位構成の大幅変化・反映遅れは保留し、最長56日で追加観測を終える。改善を確認できなければ全県へ展開しない。

変更ファイル: `app/ranking/[metric]/page.tsx`、`app/ranking/[metric]/[pref]/page.tsx`、`lib/populationTitleExperiment.ts`。テストは`tests/lib/populationTitleExperiment.test.ts`。OG/Twitter titleは現行値を保つ。現時点の差分は未コミット・未本番反映。

**完了条件:** 対象3URLだけのtitle差分を生成HTMLで確認し、非対象URL、description、canonical、H1、ソーシャルtitleに意図しない差分がない。ベースラインと本番反映日を保存できている。

**2026-10-06 build確認:** 全国・北海道・兵庫のHTMLに候補titleが出力され、北海道・兵庫の掲載数は179・41、1位は札幌市・神戸市。大阪は変更されず、OG/Twitter title・description・canonicalは既存値のまま。最終本番反映・検索結果での反映は未確認。

## 5. 対応③ 既存の比較導線改善

### 対象の分離

UI試験は`/ranking/population-growth/osaka`と`/ranking/population-growth/fukuoka`を初期対象とする。28日の検索クリックは39件・35件で、人口増加テーマは全体でも483クリックある。title試験対象の全国・北海道・兵庫とはURLを分ける。

①の計測が有効になってから14日間の基準値を取得する。対象URLのGA4セッション、既存CTA視認・クリック・比較表視認を測る。2ページで母数が足りなくても開始後に対象を追加せず、観測延長または保留とする。

### 初回の変更内容

既存の「上位3件を比較する」を主操作として明確にし、対象自治体名を近くに表示する。

```text
人口増加率 上位3自治体を比較
対象: {現在のランキング上位3自治体の名称}
```

名称・コードは現在のpodiumから取得し、固定しない。全国の上位都市への誘導や「住みやすい街」という評価には置き換えない。既存の関連リンク・診断リンクは補助操作として配置を整理する。地図導線は、その県への既存フォーカス設定を利用できる場合に補助として示し、未対応なら新しい地図機能を足さない。

リンク先は`compareHref`、`ToolSource`の既存規約を使用する。対象URLと実験variantを判別できるようにし、比較先でも入口情報を保持する。実験中のtitle、description、ランキング本文、広告配置は固定する。

CTA表示・クリックは小さなクライアントコンポーネント等で計測する。表全体や全自治体データをクライアント化しない。新規イベント案は`compare_cta_view`と`compare_cta_click`で、実験対象2URLの既存CTAへ先に計測だけ導入し、基準期間にも同じ定義を使う。変更後だけ計測して前後比較したことにしない。

### 評価と受入条件

主指標は①で定義した「対象ランキング閲覧→対象導線→比較表視認」の同一セッション成果率。補助指標はCTA視認→クリック、比較着地→データ取得成功→表視認。GA4のランディング流入・deviceも分けて確認する。

14日の基準期間後にUIを変更し、28日観測する。各期間300対象セッションを目安とするが、300件到達で有意差があるとは扱わない。変更後の主指標が相対20%以上改善することを実務上の採用目安とし、分母・成果件数・不確実性を併記する。基準成果0件の場合は相対改善率を使わない。

母数不足なら最大56日まで延長し、判断できなければ全体展開・任意選択機能への投資を保留する。検索順位・流入構成の変動も記録し、前後比較を無作為A/B試験と呼ばない。

- [ ] 対象2URLのみの表示変更で、既存の検索・比較リンクが機能する。
- [ ] モバイル幅320/375/390pxで自治体名が読め、横方向にはみ出さない。
- [ ] キーボード操作、リンク名、フォーカス表示が適切。
- [ ] 2〜3自治体のデータ取得と比較表表示が完了する。
- [ ] loading/errorを成果に数えず、実験対象・送客元を特定できる。

## 6. PR・リリース・検証

| PR案 | 内容 | 依存関係 |
|---|---|---|
| A: 計測と評価基準 | ①、③の既存CTA計測のみ、文書・必要な定義 | 最初に本番受信を確認 |
| B: 人口ランキングtitle試験 | ②、対象/対照セット、取得補助 | ベースラインと実験記録の準備後 |
| C: 比較導線の表示改善 | ③のUI差分 | Aの本番反映後、14日間の基準値取得後 |

計測の新規ロジックには、未取得データを成果としないこと、対象コードの検証、重複抑制を確認するテストを用意する。titleは試験対象の限定と年・件数の整合を検証する。文言や装飾だけを写したテストは追加しない。

各実装PRでtypecheck・test・lint・データ検証のCIを通す。metadata変更後はbuildで生成HTMLを確認し、UI変更はブラウザでモバイルとPCを確認する。変更のない同じ状態で検証を繰り返さない。

本リポジトリの`deploy-preview.yml`はpreview専用で、本番反映ではない。マージ、preview検証、本番反映を別の完了状態として記録する。本番の実際の反映経路・SHA・日時を確認し、その後に公開ページとGA4受信を確認する。

技術的な誤計測・リンク切れ・SEOメタデータ異常が出た場合は、該当PRまたはallowlistの変更だけを戻す。小さな短期変動だけを理由にロールバックしない。戻した日も実験記録へ残す。

## 7. 日程と判定

固定日より本番反映日を基準にする。`M`をPR Aの本番計測確認日、`T`をPR Bの本番反映日、`U`をPR Cの本番反映日とする。

| 時点 | 実施内容 |
|---|---|
| 実作業1〜2日目 | 現状確認・計測仕様固定・PR A作成と検証 |
| M以降 | 通常レポートへの反映を確認し、③の基準期間を開始 |
| ベースライン準備後 | PR B反映。T翌日からtitleを28日観測 |
| 有効な基準データ14日分の取得後 | PR C反映。U翌日からUIを28日観測 |
| T+28日分が取得可能になった時 | title判定。GSCの反映遅延分を待って集計 |
| U+28日分が取得可能になった時 | UI判定。GA4の反映を確認して集計 |
| 各試験の56日観測後 | 保留を終了し、採用/追加投資停止を記録 |

元レビューの10/27・11/24は進捗確認日として利用する。本番反映や基準期間の確保が遅れた場合、28日未満のデータで結論を出すために日程を合わせない。

最終成果物は、対象ごとの「実装済み・本番確認済み・観測中・採用/保留/見送り」を分けた実験記録とする。現時点は本計画文書の作成のみ完了。
